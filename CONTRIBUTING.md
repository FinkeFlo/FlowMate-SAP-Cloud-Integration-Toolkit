# Contributing to FlowMate SAP Cloud Integration Toolkit

Everyone is welcome to contribute to the **FlowMate SAP Cloud Integration Toolkit**! This project aims to stay standard-compliant, secure, and accessible to international developers.

If you are changing the docs or fixing a bug, feel free to fork and open a PR. If you want to add a new feature, please create an issue or discussion first so we can align on the vision.

---

## Getting Started

To develop the extension locally, you need [Node.js 20+ (LTS)](https://nodejs.org/) and `npm`.

```sh
git clone https://github.com/FinkeFlo/FlowMate-SAP-Cloud-Integration-Toolkit.git
cd FlowMate-SAP-Cloud-Integration-Toolkit
npm install
npm run dev
```

The dev server will compile the extension into the `.output/chrome-mv3-dev` directory. 
To load the extension into Chrome:
1. Open `chrome://extensions/`
2. Enable "Developer mode" in the top right.
3. Click "Load unpacked" and select the `.output/chrome-mv3-dev` folder.

## Project Layout

The extension is built on top of the [WXT framework](https://wxt.dev/).

| Folder | Role |
|---|---|
| `features/` | Reusable UI components and business logic, separated by domain (e.g., `message-log`, `inline-trace`). |
| `entrypoints/` | Chrome extension entry points required by WXT (background scripts, content scripts, popup). |
| `public/_locales/`| i18n dictionaries for localization. |
| `config/` | Application-wide configuration schemas. |

## Coding Standards & Conventions

1. **English Only**
   To ensure the codebase is accessible to international developers, **all code, variables, inline comments (`//`), block comments (`/* */`), and commit messages must be strictly in English**.
   
2. **Localization (i18n)**
   Do not use hardcoded text strings in UI components. All user-facing strings must be defined in the localization dictionaries (`public/_locales/en/messages.json` & `de/messages.json`). Reference them in code using the `t('key')` function exported from `features/shared/i18n.ts`.

3. **UI Framework**
   The UI is built using **Preact** (TSX), **Tailwind CSS v4**, and **daisyUI v5**. This is the single, mandatory styling stack across the entire extension (content-script overlay, Options page, Popup) — do not introduce other CSS frameworks or hand-rolled component CSS files.
   - See [`DESIGN.md`](./DESIGN.md) for the documented design tokens (colors, typography, shapes) and rationale — read this first before styling new UI. Validate changes with `npx @google/design.md lint DESIGN.md` (catches broken token refs and WCAG contrast issues) and keep it in sync with `assets/flowmate-theme.css`, which remains the actual CSS source of truth.
   - Use daisyUI component classes (`btn`, `card`, `modal`, `input input-bordered`, `checkbox`, `alert`, `badge`, etc.) first, and Tailwind utility classes for layout/spacing on top.
   - There is exactly **one** theme, `flowmate` (light), defined in `assets/flowmate-theme.css`. There is intentionally **no dark theme** — SAP Cloud Integration itself has no dark mode, so we don't need one either.
   - Every entrypoint (`entrypoints/content.ts`, `entrypoints/options/main.ts`, `entrypoints/popup/main.ts`) must import `@/assets/flowmate-theme.css` and every root HTML element must set `data-theme="flowmate"`.
   - **Shadow DOM gotcha**: the content script renders inside a Shadow Root (`createShadowRootUi`, `cssInjectionMode: 'ui'`) for style isolation from the SAP host page. daisyUI/Tailwind apply theme CSS variables via a `:root`/`[data-theme=...]` selector, and `:root` never matches inside a shadow tree. This is why `data-theme="flowmate"` must be set explicitly on the shadow container element in code (see `entrypoints/content.ts`), not just on `<html>`.
   - Only keep a component-local `.css` file if it defines a genuinely custom `@keyframes` animation with no Tailwind/daisyUI equivalent (see `features/design-tools/DesignTimeToolbar.css` for the pattern) — never for layout or color rules.
   - Keep UI components focused on rendering and decouple business logic into separate hooks or utility functions where possible.

## Git Workflow & Commits

This project uses the [Conventional Commit format](https://www.conventionalcommits.org/en/v1.0.0/) to automatically generate changelogs and better understand project history.

Here are some examples of acceptable commit messages:
- `feat: add new SAP CPI log parser functionality`
- `fix: correct typo in inline trace view`
- `docs: update setup instructions in README`

### Concise Commits & Pull Requests
Commit messages and PR descriptions should be **concise and to the point**. Avoid overly long, rambling descriptions (especially when generated by AI assistants). Focus only on the most important architectural changes and the direct impact of the code.

### Changelog Enforcement
Before **every single commit**, the `CHANGELOG.md` file must be updated with a short summary of the changes. This rule applies to all changes, even minor fixes or typos.

### Pull Request Strategy
The title of your pull request should follow the conventional commit format. When a pull request is merged into the `main` branch, **all changes will be squashed into a single commit**. The squashed commit message will use the title of your pull request to keep the Git history perfectly clean.

### Breaking Changes
If your PR introduces a breaking change, add an exclamation mark `!` after the conventional commit type (e.g., `feat!: rewrite authentication flow`). This signifies a breaking change that requires a major SemVer bump.

---

## Security & Data Privacy

**Strict Rule: Do not commit any real client names, proprietary internal project names, or sensitive tenant URLs.**

When writing documentation, creating test cases, or providing placeholder data, **always use generic dummy data**. 
- Examples of acceptable dummy data: `"Acme Corp"`, `"Contoso"`, `https://tenant.example.integrationsuite.com`.
- **Do not** use real customer names.

---

## Versioning and Releases

We follow standard [Semantic Versioning (SemVer)](https://semver.org/) driven by our Conventional Commits.

To create a new release:
1. Bump the version in `package.json` (WXT automatically syncs this to the `manifest.json` during build).
2. Document the release using GitHub Releases.
